What is shared?

Every SPIRE server in one cluster uses the same set of signing keys. Adding a server does not need another set of keys.

One set per cluster

X.509 certificates and JWT tokens use different keys. Each kind has an A slot and a B slot, so SPIRE can prepare the next key while the current one still works.

All servers can sign

Each server sends signing requests to KMS using a saved, exact key address. It does not take the rotation lock for every SVID request.

One server makes changes

A Kubernetes Lease acts as the rotation lock. One server owns it while changing shared signing state. Other servers can keep using the keys they already loaded.

“One key per cluster” does not mean one physical key in the AWS console. Current keys, prepared keys, old keys, and keys waiting for deletion can overlap. X.509 and JWT rotate separately. Disabled signing types do not need their own keys; this example leaves WIT disabled.

The normal rotation, in five steps

  1. Keep using A. One server takes the lock and prepares B.
  2. Tell clients about B. Publish its certificate or public key and save the shared record.
  3. Wait before switching. The server that will activate B must have observed the unchanged preparation marker for 20 seconds.
  4. Save the switch, then use B. Other servers see a completion marker and reload.
  5. Clean up later. A physical key is deleted only after its deadline and replacement checks pass.

The 20-second wait gives other servers time to notice the change. It is not an acknowledgement from every server, agent, or client.

Root + two subordinate clusters

They share trust, not private keys.

Root clusterIts own Lease, database records, and KMS signing keys
Signs child CA certificates · publishes child JWT public keys
Subordinate 01Its own keys and rotation lock
Subordinate 02Its own keys and rotation lock

A subordinate asks the root to sign its CA certificate. The private key stays in the subordinate's KMS key. Publishing the subordinate's JWT public key at the root does not create another root signing key.

A requested 90-day child CA is not guaranteed 90 days. Its certificate cannot outlive the parent certificate used to sign it. Readiness also checks every certificate in the installed X.509 chain. JWT keys have their own expiry, so the X.509 and JWT countdowns can differ.

If the root becomes unavailable, a subordinate can keep using its already installed signer while it remains valid and the subordinate's other dependencies work. It may be unable to prepare its next CA or publish its next JWT key.

The root may itself use AWS PCA or another upstream authority. The same distinction applies: failure to renew is different from failure to sign with an already loaded key.

When something fails

“Cannot rotate” and “cannot serve” are different.

A rotation error alone does not make an initialized server unready. The installed signers must still be valid, consistent, and not known to be blocked. Every enabled signer and every certificate in the X.509 chain must have more than six minutes left. Other health checks still apply.

Startup is different: a new process must load and validate its initial signing state. It cannot serve with a key it has never loaded.

Database grace and cached bundles

Ordinary bundle reads may reuse a previously fetched bundle for less than 96 hours during a database error. That does not promise 96 hours of successful requests. Database health has a separate configured grace period, measured from its last successful uncached check. A zero grace period gives no grace, and a process with no successful check has none either. At the deadline, database health can fail both readiness and liveness. Reading a cached bundle does not restart that timer.

If AWS may have created a key but the reply was lost

  1. Remember the attempt. SPIRE saves an attempt ID before calling CreateKey. The new key gets the same ID as a tag.
  2. Look for that exact key. Search only the matching trust domain, cluster, slot, and attempt ID. If found and validated, reuse it.
  3. Wait before trying another creation. Two successful, complete searches for the same current attempt must find no visible match at least one hour apart.
  4. Spend one extra attempt before calling AWS. Save the old and new attempt IDs together in the Lease. A crash or restart cannot give that permission back.
  5. Remember any late old key. If the earlier key appears later, keep it unused for review. Do not silently adopt or automatically delete it.

Ten extra attempts, shared by the whole cluster

The retained Lease history allows at most 10 additional recovery attempts across all signing slots. It is not ten keys per rotation. Normal successful rotations can continue after those ten are spent.

Restarts and completed rotations do not reset the quota. A restart does reset the local one-hour observation wait. Even a crash before the extra AWS call, or a definite rejection of that call, does not refund the saved authorization.

At the limit, SPIRE logs warnings and reports metrics. It keeps looking for the existing pending key, but cannot authorize another replacement. An external alert rule must deliver any notification.

What does a “complete search” mean?

The tag search can return several pages. SPIRE must read every page successfully, reach the end of pagination, and validate the returned records. An error, partial response, bad record, or repeated page token does not count. Even a complete empty search is not proof that no key exists: AWS's tag index may not show a recently created key yet.

There is no fallback that lists every KMS key and reads every key's tags. Alias listing can still return names from the account before SPIRE filters its own prefix; it must not adopt another cluster's key.

Trust must be checked before it changes

An old bundle can help serve. It cannot approve a rotation.

A bundle contains public certificates and keys used to verify identities. A cached copy may help ordinary serving during a database outage. But it may be missing a recent change.

  1. Ask the database again. Coordinated rotation, relevant child requests to the root, and coordinated bundle publishing bypass the stale-cache fallback.
  2. Stop that change if the read fails. Do not treat yesterday's bundle as proof that today's new key was published.
  3. Remember blocked keys. Keys covered by a saved taint or revocation record stay blocked after removal, restart, or an old update.

For a child's JWT publication, the root adds the public key; it does not create a new root signer. The database append rechecks the current rotation ownership and blocked-key records before saving. A later identical request can reuse the same public material instead of generating another JWK identity.

Previously trusted keys are not all deleted just because an upstream snapshot omits them. Normal expiry, pruning, and explicit taint or revoke handling have separate rules. A fresh read also does not make a later upload to S3 one atomic database transaction.

The five-minute input floor is not a usable readiness target. The rotation code accepts CA lifetimes of at least five minutes, but a five-minute signer cannot pass the more-than-six-minute readiness rule. Even a 30-minute CA normally activates its replacement with only five minutes left. Use much longer lifetimes and leave time for failures and recovery.

Automatic preparation starts with the smaller of half the current lifetime or 30 days remaining. Automatic activation starts with the smaller of one sixth of the lifetime or 7 days remaining. Parent expiry can shorten a subordinate's actual lifetime. Manual preparation does not bypass publication and consistency checks.

Old keys and cleanup

No alias does not mean “safe to delete.”

An old enabled key can intentionally have no alias. A server that has not reloaded may still hold that exact key address. Moving the alias does not change the saved address used for signing.

Normal cleanup checks the saved deadline, the old and replacement key tags, ownership, the replacement public key, and the aliases. The old key must have no alias. A missing check keeps the key and its cleanup record for a later attempt.

Due preparation and activation generally take priority over cleanup. Cleanup can run first when needed to unblock the pending creation for that same slot. There is no acknowledgement from every server before deletion.

Enabled

KMS can still use the key to sign if access is permitted. The key may be current, prepared, old, or retained for review.

PendingDeletion

KMS no longer signs with it. The seven-day wait is time before physical removal, not seven extra days of signing.

Public trust

Certificates and JWKs are separate from the private KMS key. They can remain published to verify credentials already issued.

This cluster plugin does not automatically delete another cluster's keys. A stale heartbeat or a missing alias alone does not prove those keys are unused. Retained keys from abandoned attempts and stopped clusters need review.

Names seen in KMS and in the Lease

spire-retire-token is the old key's replacement-attempt tag. spire-retire-source on the replacement names the old key. The earliest deletion time is retire_after in the Lease's pending-retirement record; it is not a spire-retire-after KMS tag.

A completed tag inventory can still show a key already in PendingDeletion. Repeated “keeping key” inventory messages do not cancel its deletion. SPIRE checks the key state and avoids another scheduling call when it is already pending deletion.

Configuration and saved records

The Lease remembers work across restarts.

The cluster identity comes from aws_kms_cluster.key_identifier_value. Every server in that cluster must use the same value. A separate ca_rotation_lock.cluster_id setting is no longer used.

The default Lease name is spire-server-ca-rotation.<cluster-id>.<trust-domain>. For the examples here it is spire-server-ca-rotation.prod-cluster.example.org. An explicit lease_name can override the default.

Normal deployments create the Lease before startup and grant SPIRE read/update access. allow_lease_creation can allow creation. A new process cannot skip required startup checks just because another replica is already serving.

Restarts and upgrades

Reuse an existing identity without creating a second writer.

  1. Record the complete key and journal state of the old servers. Choose the identity you will keep.
  2. Prepare the cluster plugin with that exact effective key identifier, shared datastore, trust domain, and Lease.
  3. Stop every old writer before starting the cluster plugin against the same aliases.
  4. Use require_existing_journal=true during adoption. Verify the same key addresses, public keys, and journal are reused.
  5. After adoption works, start the other servers. They load the same state.

Rolling restarts and scale changes are expected once all servers use compatible coordinated code and the same configuration. Do not assume that older binaries understand newer saved recovery records. Moving between versions that do not understand those records needs a planned, quiesced transition.

Migration does not erase older verification keys. JWT public keys normally become eligible for pruning 24 hours after expiry, then wait for a successful six-hour cleanup pass and the consumer's next refresh. Existing taints can be backfilled; already removed historical deny information cannot be reconstructed automatically.

The new behavior is enabled by the cluster plugin and rotation lock together. Ordinary aws_kms does not acquire this cluster-rotation behavior when they are disabled. This is a statement about this feature's boundary, not a claim that every other custom patch disappears.
