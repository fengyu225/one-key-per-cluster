AWS KMS cluster rotation: design and scenarios

This page explains how aws_kms_cluster lets all SPIRE Server pods use the same AWS KMS keys. It covers changes in Kubernetes, the SPIRE database, AWS KMS, published public keys, and each server.

The account, ARNs, UUIDs, timestamps, and authority IDs below are complete example values. They are not values from a production environment.

Design overview

All SPIRE Server pods can issue identity credentials at the same time. The Kubernetes Lease is only a short-lived lock for changing shared keys and public trust. It does not choose one server to handle all signing.

How it works

  1. Stock aws_kms uses a server-specific identifier, so each pod can have its own KMS keys and CA journal.
  2. The custom aws_kms_cluster plugin uses one fixed cluster identifier. Every server calculates the same KMS aliases for the same logical signing slots.
  3. A Kubernetes Lease lets only one server at a time change shared key data. This includes creating a key, changing the CA journal, publishing a public key, activating a signer, blocking an old public key, or scheduling an old KMS key for deletion.
  4. The Lease also records what the owner was doing. If the owner stops or a reply is lost, another server can check what really happened and continue safely.
  5. After a successful change, the owner writes a new completion UUID. Other servers see that UUID, reload the shared CA and KMS data, check that it matches, and start using the same signer without a restart.
  6. Signing uses the full ARN of the physical KMS key. It never signs through an alias. Moving an alias therefore cannot silently change the key used by a server that has not reloaded yet.

What "one key per cluster" means

It means one current physical KMS key for each named SPIRE key slot. Every server shares that key. It does not mean one KMS key for the whole cluster. SPIRE still has A and B slots for each kind of signer:

Authority type Logical key slots Public identifier What can coexist
X.509 CA x509-CA-A, x509-CA-B Certificate subject key ID The current, next, old, and waiting-for-deletion keys
JWT signer JWT-Signer-A, JWT-Signer-B JWK kid The current, next, old, and waiting-for-deletion keys
WIT signer WIT-Signer-A, WIT-Signer-B WIT public-key ID The current, next, old, and waiting-for-deletion keys

If an authority type is disabled, its slots do not create KMS keys. The simulator below enables X.509 and JWT and disables WIT.

Words used on this page

Authority

An X.509 CA, JWT signer, or WIT signer. It has a public key and uses a private KMS key to sign.

Physical key

The real AWS KMS key. Its full ARN ends in key/UUID.

Logical slot

A stable SPIRE name such as x509-CA-A. A later rotation can put a new physical key in the same slot.

CA journal

The shared database record that says which authorities are ACTIVE, PREPARED, or OLD.

PREPARED

The next key is saved and its public key is published, but SPIRE is not signing with it yet.

ACTIVE and OLD

ACTIVE is signing now. OLD no longer signs new credentials, but its public key stays available while old credentials may still need it.

Lease

A small Kubernetes object used as the shared lock and as a record of unfinished work.

ARN and alias

An ARN names one exact AWS resource. A KMS alias is a movable name that points to a key ARN.

UUID or token

A random ID. The Lease uses different UUIDs for one lock attempt, one key-create attempt, and one finished change.

SVID

An identity credential issued by SPIRE. It can be an X.509 certificate or a JWT.

JWK and JWKS

A JWK is one public JWT signing key. A JWKS is a list of JWKs published for JWT verification.

Public-key fingerprint

A SHA-256 hash of a public key. SPIRE uses it to prove that records refer to the same physical key.

1. Request A 10-second scheduled pass, a CLI call, or an upstream trust event asks for a change.
2. Observe The server reads the Lease and reloads any completion it has not seen.
3. Acquire Only one update based on the latest Lease version can win. The winner records its UUID.
4. Change The owner changes KMS, the CA journal, and public keys in a safe order.
5. Complete One Lease update publishes a completion UUID and releases ownership.
6. Reload Every server reloads, checks the values, and starts signing with the same physical key ARN.

What does each system control?

Data What it decides What it does not decide
Kubernetes Lease Which server may change shared data now, whether old work may be unfinished, when a checked change finished, and which old keys still need deletion. It does not contain private keys, CA certificates, JWKs, or the complete journal.
CA journal in the SPIRE datastore Which authorities are ACTIVE, PREPARED, or OLD, plus their public keys, IDs, slots, start times, and expiry times. It does not store a KMS ARN. SPIRE matches journal public material to a validated KMS key.
AWS KMS physical key and tags The private signing key, its fixed physical ARN, which cluster owns it, its logical slot, the create attempt, and which key it replaced. A physical key existing in KMS does not by itself mean SPIRE published or activated it.
AWS KMS alias Which physical KMS key is the agreed key for one A or B slot. The alias also gives SPIRE a stable name for finding that key. SPIRE does not sign through the alias. An alias alone is not enough proof to delete an old key.
SPIRE bundle and OIDC JWKS The public certificates and JWKs that consumers use to verify credentials. They do not choose the current private signer or prove Lease ownership.
One server's memory The ACTIVE signer that this process is using, including the full physical key ARN. Memory is not the saved record. SPIRE changes it only after reloading and checking the shared data.

Safety rules

One writer

Only the exact Lease holder and acquisition UUID may update shared rotation state.

One cluster name

The Lease cluster ID and KMS key_identifier_value must match exactly on every server.

Save before use

SPIRE saves and checks the CA journal before this process starts using a new signer.

Sign with one exact key

Each signer names one physical KMS ARN and checks its public-key hash, key type, trust domain, cluster, and plugin process.

Recovery before new work

A new owner checks and finishes old work before it starts a different change.

Stop when unsure

If required proof is missing, broken, belongs to another cluster, or disagrees, SPIRE stops instead of guessing.

Why this is a separate built-in plugin

The stock aws_kms plugin is left unchanged. Selecting aws_kms_cluster by name makes cluster behavior explicit; there is no runtime mode switch that a later configuration reload can accidentally change.

  • The server rejects aws_kms_cluster without ca_rotation_lock, and rejects the lock without that plugin.
  • Exactly one enabled KeyManager is allowed for coordinated rotation.
  • The cluster plugin must be built in and use inline, non-dynamic configuration.
  • key_identifier_file is rejected because a different value on each pod would make different sets of KMS keys.
  • Tag-based discovery is required so a successor can find an unaliased or ambiguously created physical key.
  • The new operations travel through the existing KeyManager RPC in a versioned message. The patch does not change the plugin SDK protobuf, which makes future SPIRE upgrades easier.

The CA manager asks the plugin to find or create a key, resolve one exact ARN, refresh tags, list keys that may match the journal, check an old key before deletion, and finish deletion. Only aws_kms_cluster accepts these requests. A plain key-create request is rejected because it would not include the CA history and create-attempt UUID needed after a failure.

The Kubernetes Lease

The Lease is a short-lived permit to change shared data. It also stores a small amount of information about unfinished work. It is not the full CA history. Normal SVID signing does not acquire or read it.

How the Lease is selected and checked at startup

  • The namespace comes from ca_rotation_lock.namespace, or from the pod service-account namespace when that setting is empty.
  • The name comes from lease_name. If omitted, SPIRE uses spire-server-ca-rotation- plus the first 12 hexadecimal characters of SHA-256 over trust-domain + NUL + cluster-id.
  • Production should pre-create the Lease, set allow_lease_creation = false, and grant the server service account get and update on that exact object.
  • Startup reads the Lease, checks every field used by this patch, and asks Kubernetes to test an update without saving it. A missing Lease, broken annotation, or missing permission stops startup before key changes can begin.
  • require_existing_journal = true makes an empty journal a startup error. It is required when adopting an existing per-pod setup and should remain enabled afterward.
Minimal cluster configuration example 
server {
    trust_domain = "example.org"

    experimental {
        ca_rotation_lock {
            cluster_id              = "prod-cluster"
            namespace               = "spire"
            lease_name              = "spire-server-ca-rotation-prod"
            allow_lease_creation    = false
            require_existing_journal = true
        }
    }
}

plugins {
    KeyManager "aws_kms_cluster" {
        plugin_data {
            region                         = "us-west-2"
            key_identifier_value           = "prod-cluster"
            enable_tag_based_key_discovery = true
        }
    }
}

Use require_existing_journal = false only for a genuinely new cluster with no CA journal. The cluster_id and key_identifier_value must be identical. Production should pre-create the named Lease, keep allow_lease_creation = false, and grant only get and update on that Lease.

Standard Lease fields

Field Example How the patch uses it
metadata.resourceVersion 12018 This prevents two writers. SPIRE reads the Lease, changes that copy, and sends back the same version number. If another writer changed it first, Kubernetes rejects the old copy. SPIRE reads again and retries no more than two times after the first try.
spec.holderIdentity spire-server-1_b3a764c8-305a-4de0-82f7-253d90e2b4ae The pod name plus a random UUIDv4 made when that SPIRE Server process starts. A restart gets a new value. Empty means that no server owns the Lease.
spec.leaseDurationSeconds 30 Set to 30 when a server takes the Lease. Readers wait at least 30 seconds and also honor a larger stored value. A smaller value cannot make takeover happen sooner.
spec.acquireTime 2026-08-21T07:10:40Z Set when an owner acquires. It is useful for inspection, but it is not trusted to decide expiry.
spec.renewTime 2026-08-21T07:10:50Z Set when a server takes the Lease, again just before it changes remote data, and every 10 seconds while it works. Another server checks whether this value keeps changing. It does not compare the timestamp with its own clock.
spec.leaseTransitions 12 Increases when a different server-process ID takes the Lease. It helps people inspect history, but it does not prove current ownership.
metadata.annotations Seven custom keys described below Small records about the current attempt, completed work, prepared authorities, old keys waiting for deletion, and public keys that must stay blocked. SPIRE keeps unrelated annotations unchanged.

Kubernetes also defines fields such as strategy and preferredHolder. This patch does not use them. Do not use the same Lease for another leader-election system.

Why takeover does not compare clocks

  1. A server reads the Lease. It records three values: owner ID, acquisition UUID, and renew time. It also records when this process first saw that exact set of values.
  2. Any change restarts the local timer. A renewal, a new token, or a new holder proves that the observed record is still moving.
  3. All three values must stay unchanged for a full Lease duration. A non-empty holder is not eligible for takeover until this process has observed no change for at least 30 seconds.
  4. Kubernetes still decides whether takeover wins. If the old owner renewed or another server acquired between the read and update, the version number no longer matches. Kubernetes rejects the takeover.

This stays safe even when pod clocks differ. Takeover is not exactly 30 seconds after a crash. The first observer may discover the unchanged tuple on its next 10-second pass, and only then starts its local 30-second timer.

Every custom Lease annotation

Kubernetes stores annotation values as strings. JSON examples below are JSON encoded inside those strings. An annotation that is not needed is removed instead of being saved as an empty string. If required data is broken or disagrees with other data, SPIRE stops rotation. It does not guess or create another key.

ID for the current Lease attempt

spire.spiffe.io/rotation-acquisition-token
Value
A fresh random UUIDv4 for each successful Lease acquisition, such as 7b21f0d3-63b8-4ec2-8421-9ba4c0d10487.
Written
In the same conditional update that sets the holder, duration, acquire time, and renew time.
Read
Every Lease update checks both the owner ID and this exact UUID. This includes renew, complete, release, create-record, deletion-record, and blocked-key updates.
Removed
After a checked completion, or after a clean release when no remote change started. If SPIRE is not sure what happened, it leaves the UUID in the Lease.
Why it exists
It separates this Lease attempt from every older and newer attempt. A later owner can see that this exact attempt may need recovery. It is different from the server-process UUID and the completion UUID.

What the current owner was doing

spire.spiffe.io/rotation-acquisition-phase
Value
{"token":"7b21f0d3-63b8-4ec2-8421-9ba4c0d10487","state":"mutating"}
Written
When a server takes the Lease, and again just before it may change KMS, the database, or published public keys.
Validation
The embedded token must match the acquisition-token annotation, and the state must be one of the four values below.
Removed
Together with the acquisition UUID after completion or a clean release. It stays if SPIRE is not sure whether a remote change happened.
Why it exists
It tells recovery whether the old owner only took the Lease or may already have changed another system.

ID for the last completed change

spire.spiffe.io/rotation-completion-token
Value
A fresh UUIDv4, such as 01f3aa92-14de-46ad-a087-6ea8dbaf2770.
Written
Only after the owner reloads and checks the saved CA journal, published public key, and physical KMS key ARN. A recovery owner also writes a new UUID after it repairs old work.
Read
Each server remembers the last completion UUID it loaded. When the Lease has a different value, that server reloads all shared CA and KMS data.
Lifecycle
It stays in the idle Lease. The next completed change replaces it. A request that changes nothing does not replace it.
Why it exists
It is a saved signal that tells servers to reload. It does not grant Lease ownership. It does not contain CA data. It also does not prove that every server has finished reloading.

IDs of keys that are ready but not active

spire.spiffe.io/rotation-prepared-authorities
Value
A JSON object with only known authority types, such as {"x509":"4c7d8e9fa1b2c3d4e5f60718293a4b5c6d7e8b21","jwt":"Zp8rT4ydBm7Q0vK9sFw2Xa5Ce6Nj1Lu3"}.
Written
At completion. The JSON contains every X.509, JWT, and WIT authority that is currently PREPARED.
Read
Before activation, that server process must see the exact requested authority ID stay unchanged here for 20 seconds.
Removed
When no authority remains PREPARED. If another authority type is still PREPARED, that entry remains.
Why it exists
A CA journal row alone cannot start the 20-second wait. This Lease value ties the wait to one completed and checked change, so an older database time cannot make the wait end early.

KMS key creates that may be unfinished

spire.spiffe.io/rotation-pending-creates
Value
A map from logical key ID to the original create-attempt UUID, for example {"JWT-Signer-B":"7aa3a0c7-f80b-4b27-9f8f-d8195cc96bd5"}.
Written
Before SPIRE makes a KeyManager call that may create a key. The same UUID is sent with CreateKey in the spire-create-token tag.
Recovery
A later owner keeps the same UUID and does not create another key. It may use only the physical key that has this exact UUID tag.
Removed
It can be removed early only when a trusted error proves that AWS could not have created a key. Normally it is removed in the same Lease update that completes the change, after SPIRE checks the CA journal and KMS key.
Why it exists
AWS KMS CreateKey does not accept an idempotency token. Saving this record first prevents a lost success reply from causing a second KMS key.

Old physical keys waiting for deletion

spire.spiffe.io/rotation-pending-retirements
Value
[{"key_id":"x509-CA-A","pending_create_token":"42b77089-d501-45f1-901c-e16906beaf11","expected_fingerprint":"f5416512755d4aa8fdcce784121a8acb507b7d9b19db96831db5a74aef64ade2","retire_after":1787303105}]
Fields
key_id is the SPIRE slot. pending_create_token is the new key's create UUID. expected_fingerprint is the new public key's SHA-256 hash. retire_after is the earliest deletion time in Unix seconds. The old ARN comes from the new key's spire-retire-source tag; it is not stored in this annotation.
Written
In the same Lease update that completes the change, after SPIRE proves the new key's public-key hash and proves exactly which old key it replaced. The list can hold at most 128 checked records.
Deadline
The old key cannot be deleted before its authority expires. It also cannot be deleted until at least 2 minutes and 5 seconds after completion. SPIRE uses whichever time is later.
Removed
Only after a later Lease owner checks the old-to-new key link again and proves that the old key is already PendingDeletion or is gone.
Why it exists
A slow server can keep using the old physical key ARN while it reloads. Because the deletion record is saved in the Lease, deletion can continue safely after a restart or crash.

Public keys that must never return

spire.spiffe.io/rotation-taint-tombstones

An old update, a lost reply, or a restarted server cannot add back a public key that the cluster already removed.

Acquisition phase values

State Meaning Recovery consequence
acquired The owner has the Lease but has not started changing KMS, the database, or published public keys. If it stops in this phase, recovery knows no remote change started. For a new empty cluster, the Lease can be released without writing a false completion.
mutating The owner is about to change KMS, the database, or published public keys, or may already have changed them. The next owner must read those systems and check what happened. It cannot assume that nothing changed.
recovering A new owner took over work that may be unfinished, and the old phase was valid. It handles only that old work. After checking or repairing it, the owner writes a new completion UUID. A different requested change must be tried again.
legacy-ambiguous An older patch saved an operation UUID but did not save what the server was doing. The next server assumes that KMS, the database, or published public keys may have changed. An empty CA journal does not prove that no change happened.

What the 10-second, 20-second, and other timers mean

The two 10-second timers and the 20-second wait do different jobs. A timer never gives a server permission to write. A Kubernetes update based on the latest Lease version gives that permission.

10 seconds Scheduled check: "Does this server see work that should run now?"
10 seconds Lease renewal: "Can this owner still prove that it may continue?"
20 seconds Local wait: "Has this server seen the same completion or prepared-key record for 20 seconds?"
30 seconds Takeover wait: "How long has this server seen the old owner record stay unchanged?"

The 20-second wait does not mean every server has reloaded

Each server process starts its own timer when it first reads the exact Lease value. If server 2 sees it 10 seconds after server 0, server 2 still waits its own full 20 seconds. The writer does not hold the Lease while it waits. A request that is too early returns. SPIRE then wakes that process's scheduled check just after its 20 seconds end.

The wait gives SPIRE servers time to reload. It does not prove that every pod, Agent, OIDC provider, S3 object, proxy, or client cache has refreshed.

How automatic prepare and activation times are calculated

  • Prepare at NotAfter - min(authority lifetime / 2, 30 days).
  • Activate at NotAfter - min(authority lifetime / 6, 7 days).
  • A 24-hour authority prepares 12 hours before expiry and activates 4 hours before expiry.
  • A 5-minute authority prepares 2 minutes 30 seconds before expiry and activates 50 seconds before expiry.
  • A manually forced prepare may happen earlier, but automatic activation still waits for its normal time. A forced activation can happen earlier only after that server has seen the saved prepared-key record for 20 seconds.

At the 5-minute floor, the prepare and activation thresholds are 100 seconds apart. In the worst expected case, SPIRE may need one 10-second check, one 20-second wait, and two 30-second waits while Lease ownership changes. This leaves only a little time to recover. More failures can use all of that time, so production should use a longer lifetime.

What happens when SPIRE changes a shared key

The same code handles automatic rotation, CLI requests, changes received from an upstream authority, unfinished work, and delayed deletion of old keys. The requested change differs, but all paths use the same Lease, renewal, safety checks, completion update, and server reload.

  1. A change reaches one server. It can come from that server's 10-second scheduler, a LocalAuthority gRPC call from the SPIRE CLI, or an upstream bundle event. The CLI process never touches the Lease; the server pod handling the RPC does.
  2. The server runs one key-changing task at a time. Other key-changing calls wait inside that process. Normal signing can continue at the same time.
  3. It reads the latest shared data before trying the lock. The server reads and checks the Lease. If it has not seen the current completion UUID, it reloads the journal, published public keys, KMS aliases, tags, public keys, and physical signing ARNs first.
  4. It checks that the requested change is allowed. A wrong authority ID or status fails before the server takes the Lease. To activate a key, this process must have seen its exact prepared-key record stay unchanged for 20 seconds.
  5. It tries to take the lock. The server sends the Lease version it read. Kubernetes accepts only one competing update. The winner writes its server-process ID, a new acquisition UUID, its phase, the 30-second duration, and the times. A scheduled loser stops immediately. A forced API call retries every 250 milliseconds for up to 5 seconds.
  6. It finishes old work before starting new work. If the Lease contains an unfinished attempt, this owner checks and repairs only that attempt. The new requested change must be tried again later.
  7. The owner starts renewal and reads everything again. After taking the Lease, it rereads the latest journal, published public keys, KMS aliases, tags, and public keys. It may learn that another server already completed the request. Two prepare calls therefore use the same result instead of creating two keys.
  8. The owner checks the 20-second wait again. The Lease values may have changed while the request waited. The owner cannot use an old timer to skip the wait for a newer change.
  9. The owner renews and records mutating. It renews immediately before changing another system. Saving mutating tells the next owner that KMS, the database, or published public keys may already have changed.
  10. The owner changes KMS, the journal, or published public keys. Before a call that may create a key, it saves the create-attempt UUID. SPIRE handles every result as one of three cases: no change happened, the change was saved, or the result is unclear.
  11. The owner reads back and checks saved changes. It reads the saved result, checks that the public key matches the physical KMS key, and checks any old-key deletion record. Only then may this process start using the new signer.
  12. One Lease update finishes the work and releases the lock. It writes a new completion UUID, writes or removes the prepared-key record, removes only finished key-create records, updates old-key deletion records, removes the current acquisition fields, and clears the owner.
  13. Other servers reload the finished change. On its next check, each other server sees the new completion UUID. It reloads and checks the shared data, builds a local signer for the same physical KMS key ARN, and remembers the UUID only in memory.

How KMS chooses, creates, and routes a key

A logical alias has this shape: alias/SPIRE_SERVER/example_org/prod-cluster/JWT-Signer-A. The dots in the trust domain become underscores. The cluster ID and logical key ID are not pod-specific.

Observed KMS state Decision
The alias target is valid, matches this cluster's settings, and its public-key hash is not an old key already recorded in the journal. Use that physical key. Do not create a key or move the alias.
The alias target is valid, but the CA journal shows that this physical key was already used earlier for this slot. A new physical key is required. Remember the old ARN, find or create the key for this exact create UUID, put matching replacement tags on both keys, check them, and only then move the alias.
The alias is absent and no key has the current attempt token. Create one key only if this is a new allowed attempt. Recovery-only mode refuses to create.
Exactly one valid key has the current create-attempt UUID. Reuse it. Create or repair the normal alias before using it.
More than one key has the current create-attempt UUID. Stop and keep every key unchanged for investigation.
The alias or key belongs to another cluster, has broken data, is unexpectedly disabled, has the wrong key type, or has conflicting owner tags. Stop without changing anything. An alias that looks correct is not enough proof.

The plugin turns off automatic AWS SDK retries for CreateKey. AWS does not accept a safe retry ID for this call, so an automatic retry could create two keys. SPIRE saves its own create UUID in the Lease and puts the same UUID on the new KMS key. It then checks the returned ARN, key ID, key type, allowed use, state, and public key. After an alias update, SPIRE reads the alias again and checks its target.

KMS tag glossary

Tag Meaning
spire-server-td The exact SPIRE trust domain.
spire-server-id The cluster ID in this plugin, even though the inherited tag name says server ID. It is not the pod name.
spire-key-id The logical slot, such as x509-CA-A or JWT-Signer-B.
spire-active true means SPIRE manages this key. It does not mean that the CA journal currently marks it ACTIVE.

spire-retire-token Written on the old key. It identifies the replacement attempt that is allowed to retire it.
spire-retire-source Written on the new key. It stores the full physical ARN of the old key that was replaced.

Use the alias to find a key; use the ARN to sign

After checking an alias target, the plugin builds a local signing handle. It contains the logical key ID, physical ARN, public-key hash, key type, trust domain, cluster ID, and plugin-process ID. A random secret known only to this process protects the handle. For every Sign request, the plugin checks the handle and sends the full ARN to KMS. If KMS reports a different key ID, signing fails.

A restarted plugin process has a new secret. It must check the KMS key again and build new local signing handles. It cannot use a handle made by another pod.

Prepare, activate, and retire are separate stages

Prepare

Find or create the next physical key. For X.509, save the CA certificate and chain as PREPARED in the journal. For JWT and WIT, publish the public key and save a PREPARED journal row. PREPARED means the public key is available, but SPIRE is not signing with it yet. The completion update also writes its authority ID to the Lease.

Activate

After this process has seen the same prepared authority ID for 20 seconds, save the new authority as ACTIVE and the old one as OLD. Read the saved data again before this process starts using the new physical key ARN. Then write another completion UUID.

Delete an old physical key safely

When a later rotation reuses the same A or B slot, the alias moves from the old physical key to the new one. The old key stays Enabled with no alias until the saved safe deletion time. A later Lease owner checks both keys again before asking KMS to delete the old key with a seven-day window.

Moving from active slot A to prepared slot B does not delete A. The B alias names its own physical key. A physical A key is displaced only when a later cycle reuses logical slot A for A2. This is why several valid KMS keys can coexist while every server still agrees on the current signer.

Forced rotation from the SPIRE CLI

  1. The CLI sends a LocalAuthority gRPC request. It does not call Kubernetes.
  2. The server pod that receives the request reads the Lease, reloads completed work it has not seen, checks the requested change, and checks its local 20-second wait.
  3. If another owner holds the Lease, the server polls every 250ms for up to 5 seconds. If it still cannot acquire, the request returns a retryable unavailable result.
  4. After taking the Lease, the owner reloads and checks whether another server already completed the same request. Repeating prepare returns the already prepared authority instead of creating another key.
  5. A forced prepare can happen before the normal half-life threshold, but it cannot bypass a fresh unrelated completion window.
  6. A forced activate can happen before the normal automatic activation time, but never before that serving pod has observed the exact prepared marker for 20 seconds.
  7. Taint and revoke first save a blocked-public-key record, then remove public trust. They do not directly delete the physical KMS key.

If a forced command immediately activates after prepare, it normally sees a propagation pending error. This simply means that pod has not seen the saved prepared-key record for 20 seconds. Retry after its local wait. If a load balancer sends the next request to another pod, that pod may have started its own 20-second wait later.

Scheduled rotation

  • Every server runs its own check every 10 seconds. The timers do not start together, and there is no permanent rotation owner.
  • Each check first reloads a new completion UUID and looks for unfinished work, even when no normal rotation is due.
  • SPIRE tries an old-key deletion before a normal prepare. It first handles a missing current authority, an authority that is not ACTIVE, a new key that is ready to become active, or a key that is close to expiring.
  • X.509 is checked before JWT and WIT because the journal and subordinate signing flow depend on a usable X.509 authority.
  • Each check tries to delete at most one old key: the one that has waited the longest.
  • If a scheduled check cannot take the Lease, it does not wait. It checks again later.

Failure recovery and why duplicate keys are avoided

An error does not always mean that a change failed. AWS, Kubernetes, or the database may save a change and then lose the reply. SPIRE records recovery information before remote writes, reads the saved data again after an unclear result, and repeats only work that is safe to repeat.

Failure point State left behind What the successor does
Before the acquire update commits No new holder or acquisition token Another server can acquire normally.
After acquired, before mutating A held Lease whose phase proves that no remote change started After this process sees the Lease stay unchanged for 30 seconds, it can prove that a new empty cluster did not start a remote change and can release the Lease cleanly.
After mutating, before CreateKey The acquisition UUID and phase, and normally a rotation-pending-creates entry saved before the call Reload KMS and the journal. If a trusted error proves that no key was created, clear the record. Otherwise keep this exact attempt UUID and do not create another key.
CreateKey succeeds but its response is lost The Lease maps the logical key to UUID T; the physical key has spire-create-token=T Search KMS for the exact create UUID T. Reuse one valid match. If no key is found, recovery creates nothing. If more than one key matches, stop and require investigation.
Alias update returns an error or times out The alias may or may not have moved, and both old/new physical keys remain Read the alias again for a limited time and check its full target ARN. If the answer is still unclear, keep the recovery records and leave both keys unchanged.
The database saves the change, but its reply is lost The journal or bundle may already contain the requested change Reload the database for up to 15 seconds. If the requested change is present, treat it as saved instead of writing another key version.
The process stops after saving remote data but before completion Journal/KMS/public state may be new, but the old completion UUID remains and acquisition evidence is unfinished Check and finish that old attempt, write a new completion UUID, and ask any unrelated caller to try again later.
Lease renewal fails during work The owner can no longer prove authority Immediately mark the Lease as lost and stop the running work. Even if a remote write just finished, this process cannot start using the new signer. The next Lease owner reads and repairs the saved state.
Completion update result is lost Kubernetes saved either the whole update or none of it Read the Lease again. A Kubernetes Lease update is all-or-nothing, and its version number prevents an old owner from overwriting a newer update.
Old-key deletion response is lost The saved old-key deletion record may remain even though KMS already says PendingDeletion Check that physical ARN again. If KMS says PendingDeletion or NotFound, remove only that matching deletion record. If the answer is still unclear, keep the record and try later.

Clean release, uncertain release, and completion

Clean release

No remote change was attempted. Clear the owner, acquisition UUID, and phase. Do not write a completion UUID or start a 20-second wait.

Uncertain release

Clear the owner so another server can start recovery immediately. Keep the acquisition UUID, phase, unfinished key-create record, and other recovery information.

Checked completion

Read the shared data again and prove that it has one valid result. Then update completion, prepared-key, and old-key deletion records in one Lease update, remove finished recovery records, and release the Lease.

The two ways SPIRE deletes old physical keys

Path Which keys Safety checks Result
Normal deletion after replacement An old physical key owned by this cluster. It was replaced when a later rotation reused the same A or B slot. The old authority's NotAfter time, the minimum delay after completion, logical key ID, original create UUID, new key's public-key hash, old key ARN, matching tags on both keys, and every KMS alias. A later Lease owner schedules that exact old key with a seven-day KMS window. It removes only that deletion record after AWS says PendingDeletion or NotFound.
Cleanup for a cluster that no longer exists A key with another cluster ID in the same trust domain A different cluster owner, no update for at least 14 days, the 48-hour cleanup check, complete owner tags, only expected aliases, two reads before deletion, and no evidence that the old cluster is still running. Schedules seven-day deletion only after every check passes. Keys owned by the current cluster never use this path.

Removing public keys is separate from both KMS deletion paths. Scheduling or deleting a private KMS key does not remove its X.509 certificate or JWK from the SPIRE bundle or OIDC output. Certificates and JWKs follow their own expiry, taint, revoke, and pruning rules.

Migration, scale changes, restart, and rollback

Rolling restarts are safe after every pod uses the cluster plugin and the same settings. The first move from per-pod aws_kms is different. Stop all old writers, choose one existing key set and matching journal, and then start cluster mode. Never run the old and new plugins at the same time.

Initial migration from one key set per pod

  1. Record each old pod's KMS identifier, aliases, physical ARNs, public-key hashes, journal rows, bundle certificates, JWK IDs, key policies, and current credentials.
  2. Choose one pod's existing KMS identifier and matching CA journal. Use that identifier as both the new cluster ID and key_identifier_value.
  3. Stop every old SPIRE Server process and anything that could restart one.
  4. Save the before-state from KMS, the database, the bundle, OIDC, and the empty pre-created Lease.
  5. Start one patched pod with the selected identifier and require_existing_journal = true.
  6. At first, deny KMS key creation, alias changes, and deletion requests. A safe first start should find and use the existing keys and journal without changing them.
  7. Compare the new state with the saved before-state. Check key count, alias targets, journal contents, authority IDs, completion state, certificates, JWKs, and a real KMS signing request.
  8. After all checks pass and the migration is approved, restore the KMS permissions and add more pods. Each new pod must load the same keys and journal without creating anything.

A brand-new cluster identifier does not point at the selected pod's old aliases and journal. Using a new identifier is not an in-place move; it needs a separately reviewed key namespace and trust migration. A safe in-place move keeps the selected old identifier.

What happens to old JWKs and certificates?

  • The switch does not remove authorities from nonselected stopped pods.
  • Previously issued JWT-SVIDs continue to verify because their JWKs remain in the shared bundle and OIDC JWKS.
  • Previously issued X.509-SVIDs continue to verify through their retained roots.
  • New credentials after the switch use the selected cluster's ACTIVE authority on every server.
  • An expired JWK normally becomes eligible for removal 24 hours after its NotAfter, then waits for the next successful six-hour prune and the next OIDC refresh.
  • An explicit taint or revoke follows its own public-key removal path and is protected by the saved blocked-key record.

When rolling restart is safe

After migration has completed and all pods use the same patch, cluster ID, KeyManager, Lease, datastore, and trust domain, rolling restart and scale changes are expected operations. A restarted pod gets a new boot UUID, reads the completion token, discovers the unique shared journal, resolves the physical KMS key ARNs, and joins without creating a key. It may stay not ready for a short time while it reloads and checks the shared data.

Rollback boundary

  • Before cluster mode creates a key, moves an alias, changes the journal, or schedules deletion, rollback can start one standard aws_kms pod with the selected old identifier. First stop every patched pod and compare the current state with the saved before-state.
  • After cluster mode makes any of those changes, rollback requires people to inspect and repair KMS, the Lease, the journal, and the bundle. Changing only the plugin name is not enough.
  • Never run old and new plugin pods together during rollback. Record every physical key ARN and PendingDeletion date. If an old key is needed, cancelling deletion returns it in the Disabled state. Enabling it and restoring the alias and journal must be separately approved and checked.

Expected behavior

These checks cover the main state changes:

  1. Configuration: The cluster ID, fixed key identifier, built-in plugin name, tag discovery setting, and pre-created Lease match on every server.
  2. Steady state: Three Ready servers use the same full signer ARNs and shared journal IDs. No server holds the Lease. The aliases point to the checked shared keys, and the current JWK set matches those keys.
  3. First startup: The owner creates an acquisition UUID, changes the phase, saves the create record before CreateKey, creates the journal, and finishes with one Lease update that writes completion and clears the owner.
  4. Normal rotation: SPIRE prepares the new key, saves that it is ready, waits 20 seconds, switches to the key, reloads the change on other servers, and later deletes the old key.
  5. Concurrent prepare: Kubernetes accepts one Lease update and rejects requests that used an older Lease version. Other callers return the key that is already prepared.
  6. Lost CreateKey response: The Lease and KMS tag contain the same UUID. The next owner finds and reuses that physical ARN without creating another key.
  7. Crash during activation: The renew time stops changing. Another server waits 30 seconds, finishes the old work before starting new work, and writes a new completion UUID.
  8. Migration: The selected old identifier, aliases, and CA journal stay unchanged. Old JWKs remain available, and more servers start without creating more keys.
